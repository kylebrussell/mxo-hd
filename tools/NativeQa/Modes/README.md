# Native QA fixture modes

Each sealed `NativeQaMode` subclass is discovered from this assembly and owns one mode name, an immutable `NativeQaModePlan`, and an optional after-start hook. Add a file here for a new mode; the registry and shared Program require no mode-list edit. Names are ordinal and case-sensitive as before. Unknown names use DefaultMode, with dev commands off, no GM, no forced callback rolls and the default spawn/loadout.

The plan owns ability IDs, X/Z spawn, environment privilege flags and ordered SQL stages: BeforeLoadout, AfterLoadout, AfterHelpers. Program still owns custom-loadout validation, discipline ancestors, common helper creation, snapshot copying, source/snapshot SHA equality, configured Debug/Release paths, client-lock lifecycle and shutdown. Moving these stages does not authorize running native setup. Read-only `--fixture-plan <mode>` serializes the actual environment and full plan before any setup; `--build-info` retains its provenance contract.

`StealthShieldsMode.AfterStartAsync` retains the existing bootstrap217 activation and acknowledgement output. Do not replace it with assumed server state. Its native lifecycle remains Claude-only.

When porting writer, Zen Master or Desperation, merge updated master first, add a uniquely named mode file, and move that branch's exact loadout/environment/SQL or bootstrap into the appropriate plan/hook. Preserve default/unknown behavior and avoid granting dev/GM/fixed rolls to unrelated modes. If a mode needs existing values, use explicit source helpers rather than inventing defaults. Compile-items already retains PR135's compiler bag1, ordinary2399 archive307072/level1 and separate IS refill; Disguise slot1 replacement is scoped to remaining/health-callbacks. Do not import unmerged gameplay implementations while porting fixture configuration.

`tests/hds.Tests/NativeQaLegacyPlans.json` records the20 pre-refactor plans from master cdf23ea (19 named/default configurations plus unknown fallback). Environments and metadata came from executing only the original read-only CLI; loadouts, spawn and ordered SQL came from running extracted original pure selection logic with a recording executor, never a database. Tests execute the new read-only CLI from an empty directory and compare all baseline fields. SQL literal line endings alone normalize for Windows/Linux checkout differences; SQL contents and stage ordering must match. New modes should have their own focused plan/CLI assertions rather than silently modifying the historical baseline.
