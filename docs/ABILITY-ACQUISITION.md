## Transaction and explicit server policy

Every operation owns its connection and checks that character, inventory and archive tables are already InnoDB. It performs no schema migration. Lock order is character row, inventory rows/range, then archive rows/range for learning. Queries use `FOR UPDATE` under the configured isolation. Exact inventory primary key, stored signed 64-bit GOID, slot and count protect deletion. Descriptor interpretation accepts only the union of signed and unsigned 32-bit representations. Corrupt wider values reserve archive slots but cannot alias a known ability; the delete predicate retains the exact original signed or unsigned raw value. Real archive slots are 0 through 519, and every occupied family reserves its slot. The hidden/attribute region is never allocated.

The server's explicit policies are: genuine family validation precedes canonical identity and only ordinary catalog class 0 is acquired; unknown codes and ambiguous slots refuse; canonical known duplicates retain the bag code; a full archive retains it; stacked ability codes refuse without destroying their stack. Existing rank aliases are recognized without copying code-family IDs into the ability namespace. Signed bag-row coverage belongs to this dedicated transaction; unchanged general inventory readers still require unsigned values. Normal purchases create unsigned bag descriptors. This package does not claim a general repair of corrupt or signed legacy inventory presentation. Newly learned entries preserve the existing level-1, unloaded representation. Learning does not load, train or grant anything.

The hardline's unchanged Code Bit plan reserves its pending new slots while the ability allocator runs. Ability transfers are atomic individually; this is not a new all-or-nothing bulk Code Bit transaction. Independent legacy inventory/archive writers that do not take these locks remain a documented concurrency limit. There is no global storage or inventory lock rewrite.

Handlers serialize acquisition through the existing per-player crafting lock. SQL transactions contain no mission, player-life, transport or packet callbacks. Successful receipts are returned after commit. A scalar publication stamp captures the client-data reference, character, world, life, transport epoch and district state before database reads. Success packets are encoded outside the transport fence; only matching scalar checks, the optional committed wallet-cache scalar update and direct world-bound enqueues occur inside it. Output requires a live connection, no shutdown and no pending world change. Stale character or epoch publication cannot overwrite the reused client-data wallet cache. The same captured Loading Area state is permitted without imposing a new on-world requirement. Existing pruning drops stale unassigned acquisition records after reset while ordinary reliable messages remain unchanged. A successful transaction can persist while a reset suppresses its UI response; relog recovers the durable state, rather than pretending the commit rolled back. Already-numbered reliable delivery keeps the existing policy. Mixed-upload Code Bit records and shared bulk completion remain legacy publication; this is not a broad queue rewrite. Failed SQL operations return ordinary UI notices and the existing Central Storage failure result where that route needs one; no fabricated purchase opcode or error code is added. The existing one-live-world-session model still governs handler publication order.
